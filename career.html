"내 서비스다" 생각하고 이슈를 끝까지

회원제 특허 SaaS의 6개 검색 사이트 유지보수·개선 담당으로, 대량 문서 뷰어·엑셀 다운로드·비교보기를 메인 담당. 운영하면서 마주친 코드·기획·데이터의 불일치를 그냥 넘어가지 않고 끝까지 추적해 해결하는 방식으로 일했습니다. "기능을 구현하는 사람"이 아니라 "서비스의 상태를 책임지는 사람"으로서 운영을 대했습니다.

"이슈를 발견하면 넘어가지 않고, 보고하고, 끝까지 해결했다."
대량 데이터를 다루는 회원제 SaaS — 6개 검색 사이트의 유지보수·개선. 대량 문서 뷰어·엑셀 다운로드·비교보기를 메인으로, 그 외 사용자 편의성·로그 분석·외부 API 연동·DB 마이그레이션까지 담당 영역을 좁게 한정하지 않고 서비스 전체의 상태를 능동적으로 관리했습니다.

02 · HOW I WORK

이슈를 발견·추적·해결한 방식

"내 담당 기능"의 경계를 좁게 두지 않았습니다. 운영 중 이상한 점 → 보고 → 원인 추적 → 해결을 능동적으로 반복했고, 특히 기획과 코드의 불일치를 발견하면 기획팀과 직접 의논해 정정한 경험이 많습니다.

🤝 CASE #1
기획 단계부터 함께 한 협업 — 자문 · 사용자 관점 · 코드 불일치 검토
단순 구현자가 아닌, 기획과 사용자 사이를 잇는 사람으로 일하기
기획 자문
기획 초기 단계에서 "시스템적으로 가능한 범위 · 비용 · 우회 방법"에 대한 자문을 요청받음. 받은 기획을 그대로 구현하는 게 아니라, "이 방향이 운영에 어떤 부담을 줄지"를 함께 검토.
사용자 관점
실제 사용자가 되어 서비스를 써보며 불편한 지점을 직접 체감. 기획에 적힌 흐름과 실제 사용 경험 사이의 간극을 발견하면 의견을 정리해서 공유. "사용자 입장에서 편리한가"를 기준으로 기획팀과 활발히 소통.
코드 불일치 검토
새 기획안이 나오면 받자마자 "이 구조가 지금 코드와 맞나?"를 먼저 확인. 기획팀이 알고 있는 시스템 모습과 실제 운영 중인 코드의 동작이 다른 경우를 정리해서 공유 — 어느 쪽을 정정할지 의논해서 결정.
결과
"막상 만들고 보니 의도와 다르다"는 재작업 비용을 사전에 차단하고, 기획팀도 시스템의 실제 모습을 더 정확히 알게 됨. 단순한 백엔드 구현자가 아닌, 기획·사용자·코드 사이를 잇는 사람으로 자리매김.
🔍 CASE #2
운영 중 이상 패턴 → 원인 추적 → 사전 차단 기능 개발
"넘어가지 않는 사람"의 실제 작동 방식
상황
문서 업로드 시 가끔 특정 Exception이 발생해 파싱 실패하는 케이스가 있었음. 보통은 "사용자 문서가 이상한 거겠지"하고 넘길 수 있는 산발적 에러.
행동
그냥 넘기지 않고 Exception 패턴을 모아서 분석. Apache POI가 던지는 특정 Exception이 사내 E-DRM 암호화 문서의 시그널임을 식별. 무작위처럼 보이던 에러가 실은 일정한 원인이 있었음.
결과
업로드 단계에 사전 검증 필터를 두어 "암호화 해제 후 재업로드" 안내. CS 문의 사유 중 해당 케이스를 사전에 차단. 단순 에러 처리가 아닌, 원인을 끝까지 추적했더니 운영 부담 자체가 줄었음.

04 · DEEP DIVE — DB MIGRATION
🗄️ DEEP DIVE — DB MIGRATION
PostgreSQL → MSSQL 마이그레이션 후 슬로우 쿼리 개선
시행착오로 풀었던 작업, 이제는 원리로 설명할 수 있는 사례

P · 팀 차원에서 PG → MSSQL 전체 이관을 진행. 마이그레이션 후 특정 쿼리가 눈에 띄게 느려진 케이스를 제가 담당해 개선.

A · 같은 결과를 내는 여러 SQL 형태를 시도하며 단계적으로 접근:

  • ① 호출 경로 식별 — 영향 범위 먼저 파악
    슬로우 쿼리가 발생하는 화면·기능을 먼저 식별해 회귀 검증 범위를 가늠. 이유: 쿼리만 보고 고치면 같은 쿼리가 호출되는 다른 화면에서 회귀가 날 수 있음.
  • ② 서브쿼리 ↔ JOIN ↔ UNION 변환 시도
    서브쿼리로 짠 부분을 JOIN으로, JOIN을 UNION으로 바꿔보며 MSSQL에서 어떤 형태가 빠른지 실행 시간 측정으로 비교. 결과: 일부 쿼리는 개선, 일부는 미미.
  • ③ WHERE절 구조 조정
    조건 순서·표현 방식을 다양하게 시도. 결과: 미미한 개선. 근본 해결은 안 됨.
  • ④ 임시 테이블로 단계 분할 — 결정적 해결
    복잡한 한 방 쿼리를 단계별로 쪼개서 임시 테이블에 넣고 다음 단계에서 사용. 결과: 큰 개선 확인. 이게 결정적이었음.

R · 벤더가 바뀌어도 기존 환경 대비 동일 수준의 응답 성능 유지하며 슬로우 쿼리 개선 완료.

📚 솔직히 — 당시엔 잘 몰랐고, 지금은 설명할 수 있음 당시엔 옵티마이저나 Hash Join 같은 개념을 깊이 알지 못했고 시행착오로 풀었어요. 지금은 MSSQL 옵티마이저가 복잡 쿼리에서 통계 추정이 빗나가면 인덱스를 두고도 Hash Join으로 떨어진다는 것, 임시 테이블 분할이 옵티마이저 의존성을 줄이는 효과가 있다는 걸 이해합니다. 다시 만나면 실행 계획부터 먼저 보고 접근할 거예요.
→ 학습 연결 고리
이 경험에서 SQL 의존성·벤더 종속성의 한계를 체감 → ORM(JPA) 학습 동기로 직결 → 영속성 컨텍스트·벤더 독립 데이터 접근 계층 설계를 학습 → 부트캠프 프로젝트의 JPA + QueryDSL 설계에 적용.
05 · DEEP DIVE — CONCURRENCY
⚡ DEEP DIVE — CONCURRENCY
임계구역을 "긴 로직 뒤"가 아닌 "맨 앞"으로 옮긴 비동기 동시성 설계
1만 건 분할 비동기 처리에서 다중 창 동시 요청을 통한 한도 우회 원천 차단 + 비동기 모니터링 누락 제거

P · 1만 건 규모 다운로드를 100건씩 분할 비동기 처리하는 회원제 기능에서, 이용량을 모든 처리 완료 후 집계하는 구조 → 사용자가 여러 창에서 동시에 다운로드하면 검사 시점에 한도가 비어있어 제한 우회(race condition). 비동기 특성상 실패 다운로드의 모니터링 알림도 누락.

A · 임계구역의 위치 자체를 재설계 — 옵션별로 트레이드오프 비교:

대안 검토 — 동시성 보호 옵션 비교

REJECTED · DB 락
SELECT ... FOR UPDATE
비동기 처리 시간(수 초~수십 초) 동안 락 점유 → 처리량 저하 + 다른 정상 요청까지 블로킹.
REJECTED · 분산 락
Redis · ZooKeeper
단일 DB 환경에 오버엔지니어링. 외부 의존성 추가 + 운영 복잡도 상승. 본 문제는 DB 한 곳에서 풀 수 있음.
CHOSEN · 임계구역 재배치
사전 차감 (Front-loading)
이용량 집계를 critical section 가장 앞으로 이동하고 사전 차감 방식 전환. 락 없이도 race 차단 + 실패 시 롤백 가능.

R · 동시 다발 요청을 통한 이용량 제한 우회를 원천 차단, 비동기 환경 모니터링 누락 제거.

📚 부트캠프에서 락을 공부하고 알게 된 것 당시엔 "여러 방법 중 사전 차감이 맞다"는 판단으로 풀었는데, 이후 공부해보니 락 기반으로도 풀 수 있다는 걸 알게 됐어요. 비관적 락(PESSIMISTIC_WRITE)으로 차감 row를 잠그거나, 낙관적 락(@Version)으로 충돌 시 재시도하거나. 단 우리 환경엔 처리 시간이 길어 락 대기가 부담이라 사전 차감이 더 맞았습니다 — 이제는 환경에 따라 도구를 선택할 수 있게 됐어요.
→ 학습 연결 고리
"긴 로직 이전에 임계구역을 둔다"는 동시성 설계 원칙을 체득 → 부트캠프에서 분산 락·동시성 제어를 자청 발표(낙관·비관·분산 락 트레이드오프) → da2조부 프로젝트의 seq 채번 race condition에서 의식적으로 비관적 락(PESSIMISTIC_WRITE) 선택. 3단계 학습 곡선의 시작점.
06 · DEEP DIVE — STREAMING UX
⚡ DEEP DIVE — STREAMING UX
대용량 문헌 실시간 번역 — 원문 우선 렌더 + 비동기 도착 구조
실측으로 좋은 솔루션을 찾았고, 알고 보니 정식 패턴이었던 사례

P · 특허 문헌 200건을 백엔드에서 전부 번역 완료 후 응답하는 방식 → 사용자가 첫 결과까지 너무 오래 기다림. 운영 환경에서 사용자 이탈 위험.

A · "프론트 먼저 + 비동기 번역 덮어쓰기" 구조를 가정하고 실측 비교로 우월함을 확인. 프론트와 협업해 응답 처리 흐름 재설계.

  • ① 원문 즉시 렌더
    사용자 요청 즉시 원문을 화면에 표시 → 대기 시간 0. 핵심: 사용자는 원문을 읽기 시작하면서 번역을 기다림.
  • ② 백엔드 병렬 비동기 번역
    200건을 순차가 아닌 병렬로 번역 요청 → 전체 처리 시간 단축. 이유: 외부 번역 API 호출은 네트워크 대기 시간이 커서 병렬화 효과가 큼.
  • ③ 도착 순서대로 점진 교체
    번역이 도착하는 대로 화면의 원문을 자연스럽게 교체 → 사용자 체감 응답성 향상. 재사용: 이 비동기 갱신 구조는 이후 이미지 팝업 실시간 동기화에도 동일하게 적용.

R · 첫 결과 도달 시점이 크게 단축됨. 사용자는 원문을 즉시 읽으면서 번역이 도착하는 걸 자연스럽게 봄.

📚 알고 보니 — 이게 정식 UX 패턴이었음 이후 공부해보니 이게 Streaming / Progressive Rendering 패턴이라 부르더라고요. Time to First Byte 단축이 체감 응답성을 결정한다는 원칙이고, HTTP 스트리밍·SSE·GraphQL @defer 같은 표준이 같은 철학에서 나왔어요. 당시는 직접 구현했지만, 다시 만나면 SSE 같은 표준 프로토콜이나 viewport 우선순위 큐도 함께 검토할 거예요.

08 · GROWTH MAP

실무 한계 → 학습 동기 → 부트캠프 적용

실무에서 시행착오로 풀어낸 문제들이 그대로 "왜 그게 효과 있었는지 알고 싶다"는 학습 동기로 이어졌습니다. 이론으로 채운 다음 다시 프로젝트에서 검증한 사이클이 두 번 완결됐어요.

🔄 GROWTH CYCLE #1 — SQL · 벤더 종속성 · DB 깊이
PG → MSSQL 슬로우 쿼리 시행착오 → ORM 학습 + 실행 계획 공부 → 부트캠프 프로젝트 적용

실무 · 100% MyBatis 환경에서 슬로우 쿼리를 경험적 시행착오로 풀었지만, "왜 효과 있는지" 설명할 수 없는 부분이 마음에 남음.

학습 · 영속성 컨텍스트·JPQL·벤더 독립 데이터 접근 계층 설계를 학습. 옵티마이저·실행 계획·카디널리티 추정 개념도 함께 정리. "왜 ORM이 필요한지"를 실무 경험으로 설명 가능.

적용 · 부트캠프 프로젝트에서 JPA + QueryDSL로 데이터 액세스 계층 직접 설계. PostGIS 같은 벤더 특수 기능은 Native Query로, 일반 도메인은 JPA로 — 이 분기 기준도 실무에서 체감한 한계로부터 나온 판단.

🔄 GROWTH CYCLE #2 — 동시성 제어
비동기 다운로드 race 직감으로 해결 → 락 트레이드오프 발표 → da2조부 비관적 락 의식적 선택

실무 · "긴 로직 이전에 임계구역을 둔다"는 방식으로 race를 풀었지만, 어떤 락이 어떤 상황에 맞는지 체계적으로 모름.

학습 · 부트캠프 스터디에서 낙관적/비관적/분산 락 트레이드오프를 자청 발표. 각 락의 동작 원리·임계구역 크기·충돌 빈도에 따른 선택 기준을 코드 레벨로 검증.

적용 · da2조부 프로젝트의 seq 채번 race condition에 비관적 락(PESSIMISTIC_WRITE) 적용. 분산 락도 검토 후 "단일 인스턴스 토폴로지엔 오버엔지니어링"이라는 판단으로 배제 — 여러 옵션을 알고 의도적으로 선택한 사례.
